# 评估方法论

本文件规定 JD 拆解、评分、证据引用与核查的规范，供每次筛选时遵循。

## 1. JD 拆解规范

把 JD 拆成三类，**每条都要引用 JD 原文**（保留原句或关键短语）：

| 类型 | 判定标准 | 例子 |
| --- | --- | --- |
| 硬性要求 | JD 明确写死、不满足即不合格：学历、专业、工作年限、硬技能、证书、到岗时间等 | "本科及以上"、"3 年及以上运营经验"、"熟练使用 SQL" |
| 加分项 | 有更好、没有也能接受：行业经验、特定场景、更高学历、稳定性等 | "有电商行业经验优先"、"有从 0 到 1 经验优先" |
| 模糊项 | 无法客观量化的软素质描述 | "沟通能力强"、"抗压能力强"、"思维活跃" |

拆分完成后**先展示给用户确认**再继续：用户可能补充内部潜规则（如"只要男生/不要频繁跳槽"这类不写在 JD 里的要求）。把用户补充的要求也记入清单，并标注"用户补充"。

## 2. 评分与结论规则

- 分数范围 0-100，整数。
- **硬性要求一票否决**：任一硬性要求明确不满足 → 淘汰（除非用户另行说明可放宽，放宽时记入 notes）。
- 加分项累计加分；模糊项**只依据简历中的行为证据**判断，不能仅凭自我评价。
- 建议维度（可按 JD 临时调整，调整时向用户说明）：
  - 硬性达标：50 分
  - 岗位经验匹配：25 分
  - 技能匹配：15 分
  - 软素质/加分证据：10 分
- 结论建议：≥80 通过；60-79 待定；<60 淘汰。若 JD 差异大（如高要求岗位），可向用户提议调整阈值并确认。
- 结论必须与分数一致；若硬性不满足但分数仍高（如 70+），必须检查是否为误判。

## 3. 证据引用规范

- 每条判断（匹配、缺口、风险）**必须引用简历原文片段**，用 `jd_requirement ↔ resume_snippet` 成对呈现。
- 保留关键信息，超长句子可截断并加省略号，但不得改变原意。
- 区分「明确证据」与「推断」：推断在 evidence 的 assessment 中标注"部分匹配"，或在 questions 中转为待核实问题。
- 简历里找不到对应内容时写"未提及"，**禁止脑补**。
- 时间线按"年-月"核对，注意断档、重叠、倒序异常。

## 4. 简历核查注意点（中文简历常见陷阱）

- 职责措辞夸大："负责" vs "参与"、"主导" vs "协助"，注意区分。
- 技能列表堆砌但正文无应用证据（如"精通 Python"但无任何项目使用）。
- 项目/公司规模含糊（"亿级用户项目"但无具体角色与数字）。
- 时间断档、频繁跳槽、同岗位多次 3-6 个月离职，需进 questions 核实。
- 千篇一律、模板化/AI 痕迹明显的自我评价，建议提示用户人工复核真实性。
- 到岗时间、期望薪资、现居城市等事实字段与 JD 的匹配度单独核对。

## 5. 输出规范

- 默认**不把身份证号、完整手机号、邮箱等敏感信息写入 Excel**；如用户需要联系方式，先征求用户确认。
- Excel 里每份候选人给出 1-3 个最有价值的待核实问题（不是堆问题，而是最影响决策的那几个）。
- 生成 Excel 后先向用户展示总表摘要（结论分布 + 重点核实对象），用户反馈调整后再定稿。
- 同一批简历先按 text_hash 去重提醒（脚本会自动提示），重复投递在 notes 中标注。

## 6. 分批规则

- 建议每批 ≤30 份；超过 30 份分多批评估，最后合并 Excel（或提醒用户分批导入）。
